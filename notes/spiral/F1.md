## Findings summary (verdict per question)

**(a) Multi-glyph rows: whole-row ink box, both axes. [Measured]** The warp normalises `u` by the ink
box of the *entire line* and `v` by the ink height of the entire line (not per glyph). Whole-row model
vs per-glyph model, max corner error against the baked outline: ◢◢ 0.049 pt vs 75.6 pt; ◢◢◢ 0.042 vs
206.6; ◢▲ 0.056 vs 75.6; Consolas ▲▲ 0.027 vs 75.6, ▲▲▲ 0.033 vs 131, ▲▲▲▲ 0.040 vs 176.6. Mixed heights
(◢▪, ink heights 50.41 and 15.75) separate the `v` rule: whole-row `v` 0.034 pt, per-glyph `v` 26.0 pt.
So `a = Δu = (glyph ink width)/(row ink width)` with the row measured from the first ink to the last ink.
W's assumption is confirmed.

**(b) Arch/Button pour presets are exact polar maps with the right windows; between corners they are
Bézier fits of the same quality as Circle Pour. [Measured + Spec + Wolfram]**
- UI names: `Arch: Warped` (textArchUpPour, COM 8), `Arch: Warped Down` (textArchDownPour, 9),
  `Warped Circle` (textCirclePour, 10), `Warped Button` (textButtonPour, 11). Saved XML `avLst` is empty for
  all, so defaults are the spec's: ArchUp adj1 = 180° (cd2), adj2 = 50000; ArchDown adj1 = 0, adj2 = 25000;
  Button adj1 = 180°, adj2 = 50000.
- Measured geometry (◢, square box, 180°/180° sizes): **Arch Up** and **Button**: guides = upper
  semicircles, outer R (ink top, v = 0) and inner **R/2**, start 9 o'clock, sweep +180° (clockwise via
  12 o'clock). **Arch Down**: lower semicircle, sweep −180° from 9 o'clock, ink top goes to the *inner*
  circle **R/4** and ink bottom to R (so v = 1 is the outer circle). Single-line **Button Pour is
  identical to Arch Up Pour for every box size n = 10..42** (same nodes, same spans); its other four paths
  (two straight lines, two bottom arcs) are for lines 2 and 3 [Spec; not tested with several lines].
- Exactness against the ideal ruled polar map (`F(u,v) = (1-v)·P0(u) + v·P1(u)`, angle linear in `u`):
  corners within 0.06–0.74 pt (typical 0.1); between corners the baked outline deviates by
  (max / rms, as % of R): Arch Up/Button ◢ 2.8 / 1.0, ▲ 3.4 / 1.7; **Arch Down ◢ 3.0 / 1.5, ▲ 5.4 / 2.8
  (7.6 pt at R = 140.4)**; Circle ◢ 2.8 / 1.0, ▲ 2.8 / 1.3 (cross-check of P1b's 3.07 %). So the
  idealisation category is (b) as before, a little worse for Arch Down where the band is 4:1.
- Windows [Wolfram, symbolic `Simplify` = 0, and measured radius ratios rmax/rmin = 2.00 (Up) and 4.00
  (Down)]: an edge with ink data `(a = Δu, h = Δv, w₀ = lowest radial fraction)` becomes exactly
  `z = C + λ e^{iκ} ψ e^{iψ}`, `ψ ∈ [Θ a (κ_ρ + w₀)/h, Θ a (κ_ρ + w₀)/h + Θ a]`, where `Θ` is the guide sweep
  (2π circle, π arch/button) and `κ_ρ = ρ/(R−ρ)` (1 for ρ = R/2, 1/3 for ρ = R/4). Single glyph windows:

  | preset | ◢ (a = h = 1) | ▲ each edge (a = ½) |
  |---|---|---|
  | Circle (Θ = 2π, κ = 1) | [2π, 4π] | [π, 2π] |
  | Arch Up / Button (Θ = π, κ = 1) | **[π, 2π]** | **[π/2, π]** |
  | Arch Down (Θ = π, κ = 1/3) | **[π/3, 4π/3]** | **[π/6, 2π/3]** |

  Arch Down reaches ψ₁ = π/3 (ratio 4) and Arch Up halves the Circle windows; rows use the same formula
  with `a = 1/n`-type fractions (not measured on the arch presets, only the single-glyph case was).
- Other presets with circular guides: only these four. Ring Inside/Outside and Warp Up/Down (`textCanUp/Down`)
  have two *equal ellipses with shifted centres* (Ring: semi-axes (w/2, 0.3 h), centres vc ∓ 0.2 h) [Spec,
  evaluated with the ECMA guide formulas; not measured]. Their ruled map is "circle + linear drift in a
  third parameter, with arclength-of-ellipse as the parameter" so a straight edge is **not** a spiral
  there [Heuristic].

**(c) Character spacing and size: only preset values are exact, and the layout snaps everything to whole
96-dpi pixels (0.75 pt). Δu follows the snapped values exactly. [Measured]**
- Spacing presets (Home ▸ Font ▸ Character Spacing menu): Very Tight −3 pt, Tight −1.5, Normal 0,
  Loose +3, Very Loose +6 (COM `Font.Spacing`). Flat advance of a 72 pt ◢ row changed 60.0 → 57.0 / 58.5 /
  60.0 / 63.0 / 66.0 pt: exactly by the preset (all are multiples of 0.75 pt).
- Font dialog ▸ Character Spacing tab: *Spacing* combo (Normal / Expanded / Condensed) and *By* spinner,
  step **0.1 pt**, shows 1 after choosing Expanded or Condensed, minimum 0. But the layout rounds spacing to
  whole pixels: By 0.1 → advance +0.00; 1.0 → +0.75; 1.7 → +1.50; Condensed 0.1 → 0; 0.4 → −0.75; 1.0 → −0.75.
  So reachable extra spacing = `0.75·k pt`, `k ∈ ℤ`.
- Font size: Home ▸ Increase (A^) / Decrease (A-v) step the list 1, 2, …, 8, 9, 10, 10.5, 11, 12, 14, 16, 18,
  20, 24, 28, 32, 36, 40, 44, 48, 54, 60, 66, 72, 80, 88, 96, then ×1.2 rounded: 115, 138, 166, 199, 239, 287,
  344, 413, 496, 595 (symmetric on the way down; below 8 it steps 7, 6, …, 1). The Home size *dropdown*
  looked disabled while a warp was active (A^ / A-v worked). The Font dialog size spinner steps 0.1 pt
  (72.1, 72.2, …), but the glyph scale snaps to integer pixels per em: effective size `= 0.75·round(4S/3)`
  (80 → 80.25, 88 → 87.75, 96 → 96.0). Ink widths and advances measured at 72, 80, 88, 96 pt for the ◢
  fallback glyph: advances 60.0, 66.75, 73.5, 80.25 pt (= round(0.8333·ppem) px), widths 48.90, 54.51,
  59.60, 65.20.
- Consequence [Heuristic]: `a = w/((n−1)·m + w)` with `m = 0.75·(integer px)` (advance + spacing) and
  `w` = ink width at the snapped size. Because `k` is free, `m` takes every integer-pixel value, so `a`
  runs through a dense set of rationals; W's "all of (0, 4π]" claim survives, but only through this
  quantised set. Corner positions in warped rows were reproduced to ≤ 0.06 pt from the *snapped* flat
  layout for all five presets.

**(d) Rotated text: [Measured]**
- Text Options ▸ Textbox ▸ Text direction ▸ *Rotate all text 90° / 270°*: on a text box this writes
  `bodyPr vert="vert"/"vert270"` **and** `xfrm rot="5400000"` (COM `Rotation = 90`). Result: warped
  output is the horizontal-text output **rotated rigidly by +90° / −90° about the box centre**
  (Hausdorff ≤ 1.5 pt, Bézier noise; as a frame model, corners 0.049 pt). The `(u, v)` frame rotates with
  the text, so **no new windows** (W's "rotated text swaps (a, h)" is false for this route).
- *Stacked* (`wordArtVert`, also `rot = 90°`): the warp's `u` runs **along the stack** and `v` across the
  glyph width (best frame fit 0.055 pt for ◢◢ and 0.042 pt for ◢◢◢). Segoe UI Symbol ◢ at 72 pt: ink 50.41,
  line pitch 111.75 pt (flat ink box 50.41 × 162.16 for n = 2, × 273.91 for n = 3). So each glyph has
  `a = 50.41/(50.41 + (n−1)·111.75)` = 0.3109 (n = 2), 0.1840 (n = 3) and `h = 1`: windows
  `[2πa, 4πa]` = [1.953, 3.907] and [1.156, 2.313] [Wolfram]. This is a new `a` family (stack pitch, not
  advance), with `h = 1`; it does not give `a/h > 1`.
- Shape rotation (Rotate menu ▸ Rotate Right/Left 90°; Format Shape ▸ Size ▸ Rotation spinner, step 1°):
  rigid rotation of the whole warped output about the box centre. **Flip Horizontal / Flip Vertical** (Rotate
  menu): **exact mirror** of the warped output (0.0 pt), a UI route to the opposite-handed spiral.
- "Do not rotate text": **no such checkbox** in the Format Shape pane of this build for a text box or an
  autoshape rectangle (Text Options ▸ Textbox lists Vertical alignment, Text direction, autofit radios,
  margins, Wrap, Columns). [Open] whether `upright="1"` is reachable by another UI route.
- Autofit radios are greyed while a warp is active (set *Do not Autofit* before warping).

**(e) Box sizes with full guide spans (square n/10 in, ribbon spinner steps, ◢). [Measured]** The 360°
(circle) and 180° (arch) spans are each 100 % or 176.30° / 352.64° (= nominal·(1 − 1/49)). Each guide
independently; the shorter span makes the map non-polar. Sizes where **both** guides are full:
- **Warped Circle** (n = 28..42 re-measured with ◢; matches P1b's table at all 15 sizes): 29, 33, 35, 37, 40,
  42; with P1b: **10, 20, 21, 23, 29, 33, 35, 37, 40, 42**.
- **Arch: Warped** and **Warped Button** (identical): n = **10, 11, 12, 14, 18, 19, 20, 21, 22, 23, 24, 25, 27,
  28, 35, 36, 38, 40, 42**. Not full: 13 (inner), 15, 16 (outer), 17 (inner), 26 (inner), 29, 30 (outer), 31 (inner),
  32 (outer), 33, 34 (inner), 37, 39, 41 (outer).
- **Arch: Warped Down**: n = **11, 12, 17, 18, 22, 23, 24, 25, 31, 34, 35, 36, 39, 41**. Not full: 10, 14, 15, 16,
  19, 20, 21, 27, 28, 29, 30, 32, 33, 38, 40, 42 (outer guide short), 13, 26, 37 (inner short).
No rule found (as in P1b); the pattern is chaotic in n. There is no UI readout of the span, so a human must
check the shape (a short span turns the radial seam into a chord). Non-square boxes for the arch presets
were not tested [Open].

## Method notes

- Bake: duplicate the shape, Merge Shapes (Combine) with a 2×2 dummy, save a copy, parse `custGeom` (EMU),
  delete the result. The flat reference is the same bake with `WarpFormat = 0` on the duplicate, so the
  ink coordinates `(x, y)` of every glyph vertex come from PowerPoint's own layout (no font-file
  assumptions). Predicted corners `F(u, v)` use the spec guides with angle-linear parameter (exact for
  circular guides); compared with all baked nodes (corner error) and with dense Bézier samples (between).
- **Font caveat found on the way.** Typing `Consolas` in the Home font box changed only the Latin typeface;
  U+25B2/U+25E2 are drawn with the run's `ea` typeface, which stayed `Segoe UI Symbol` (set when I first
  chose Segoe UI Symbol with ◢ selected). So my first "Consolas ▲" rows were really Segoe UI Symbol ▲.
  Home ▸ Clear All Formatting removes `ea`; then Consolas is used. Consolas ▲ (72 pt): ink 39.59 pt, advance
  39.75 pt, `a(n=2) = 0.4990`, single edge `u`-extent 0.2495 (W's ¼ is 0.2 % off because of the pixel
  snap). ◢ in a Consolas run falls back to another font (ink 48.90, advance 60.0), not Segoe UI Symbol
  (ink 50.41, advance 62.25): **the font of ◢ must be fixed to read the window off**. Choosing
  `Segoe UI Symbol` in the Home font box sets both `latin` and `ea` (checked in the XML).

## Other things noticed

- A stray click in the first session applied a Quick Style (blue fill) to my shape and opened Format
  Background; undone with Ctrl+Z (which also reverted my *Wrap text* change; re-applied where needed). Fill
  is irrelevant to the baked geometry.
- Merge Shapes of a **filled autoshape** returns only the autoshape outline (no text), so only text boxes
  can be baked this way; a 1-glyph box and a warped box give the same bake path as in P1.
- Insert ▸ Symbol with font Consolas and code 25B2 inserts into the existing run formatting (it does not
  reset `ea`); in a *new* text box it writes only `latin = Consolas`, giving a true Consolas glyph.
- Rotation via the pane (step 1°) and via the ribbon Rotate menu are both rigid; combined with the existing
  `rotate` axiom no new arcs arise from shape rotation or flips. The new, UI-only things are (i) Arch Up/Down
  windows (Θ = π, κ = 1 or 1/3), (ii) Stacked `a` values, (iii) spacing/size-quantised `a` values.
- The Home font-size *dropdown* appeared greyed with a warp active, yet the same list is available through
  A^ / A-v and the Font dialog.
- Box-size dependence is purely a function of EMU size: the same 176.30 / 352.64 artefact (factor 48/49)
  appears for Circle, Arch Up, Arch Down and Button.
- Open from W still unresolved by F1: isolating a sub-arc with `restrict`; arch presets on rows and on
  non-square boxes; Button Pour with 2 or 3 lines; Ring and Can presets (ellipse guides) not measured.
