# P3: what a PowerPoint chart draws exactly, and how charts combine functions

**Verdict: NEGATIVE for the wishlist. No chart route draws `cosh`, `tanh`, the logistic, `ln cos`,
`x/sqrt(1+x^2)` or a true spiral exactly.** Every exact curve a chart draws is one of: a trendline of the
single-term form `p(X)`, `a e^{bX}`, `a X^b`, `a ln X + b` (with `X = x`, `2^u` or `10^u`); a Catmull-Rom
cubic-Bezier chain through data nodes; a straight polygon; or a circular arc. Charts never add or multiply two
series as *functions*; stacking adds *data values* at finitely many nodes. Three small positives are recorded under
"Other things noticed" (data-determined real exponents, Gompertz-type sigmoids, radar polar polygons).

Backend: every number below comes from PowerPoint's own `Chart.Export(path,"SVG")`, read back in Python, with fits
computed by numpy ([Measured]). No Wolfram was needed. Residuals are in SVG px (1 px = 0.83 pt of chart).
Scripts and SVGs are in the scratchpad `P3\` folder (lib.py, e1..e8.py, g1.py). COM was used only to build test
charts and to observe. The test data were written with COM; the *shape* of each curve does not depend on how the
numbers reached the sheet, but a UI route can only use fill-handle series (see "Other things noticed" 4).

## Method

[Measured] `Chart.Export(file,"SVG")` returns exact vector paths: series as `C` (cubic) / `L` segments, trendlines
as dashed `L` paths, gridlines as `L`. `Slide.Export` to EMF does **not** contain the series (the EMF+ stream holds
only gridlines and text), so use the chart-level SVG. Calibration used the gridline rectangle with axis min/max fixed.
Quirks: only the first `Chart.Export` per presentation works (later ones return 0 bytes), so one presentation per
chart; reading `Trendline.DataLabel.Text` through COM crashed PowerPoint; closing the last presentation quits it.

## What does NOT work, with evidence

- **Trendlines on stacked series.** [Measured, COM] `Trendlines().Add` is refused for stacked line, 100% stacked
  line, stacked area, 100% stacked area, radar (all three), pie, doughnut, surface, 3-D line/area and waterfall. It
  succeeds on line, area, column, bar, scatter, bubble and stock charts. So there is no "trendline of a sum".
  (Refusal observed through COM only; the UI should grey these out, [Heuristic].)
- **No function-level arithmetic.** Series are combined only by stacking, which sums *values* at discrete
  categories. Smoothing the stacked line gives a Catmull-Rom interpolant of those sums; it approximates `cosh`-type
  sums with error O(h^4) but is not the function. Category (c).
- **cosh, tanh, logistic, ln cos, x/sqrt(1+x^2).** [Proof sketch] A trendline gives `p(2^u)` with `p` a polynomial
  of degree <= 6 (u scaled or reversed), `a e^{b 2^u}`, `a 2^{bu}`, `a x^b`, `a ln x + b`. `cosh(u ln 2) =
  (2^u + 2^-u)/2` has a negative power of `2^u`, so it is not a polynomial in `2^u`. `tanh` and the logistic are
  rational but not polynomial in `2^u`. `ln cos` and `x/sqrt(1+x^2)` are in none of these families. Not reached.
- **Log y.** [Measured via COM] `Axes(2).ScaleType = xlScaleLogarithmic` is *accepted* on both axes. Project memory
  says the UI offers it only on x. I did not check the UI, so a UI-reachable log-y is [Open]. If it were reachable it
  would add `log p(x)`-type curves.
- **Smooth radar / polar trendline.** Radar has no smoothing and no trendline, so no polar curve beyond polygons.
- **Secondary axes.** My COM setup of a secondary axis failed. Spec-wise a secondary axis is an independent affine
  map of the plot area [Heuristic], so no new curve. [Open] to measure.

## Rendering and idealization notes

- [Measured] A trendline is not stored as a function: the chart renders a polyline whose vertex count scales with
  chart width (320 / 720 / 1120 vertices for 300 / 600 / 900 pt wide charts, about 2.3 vertices per SVG px), vertices
  snapped to integer px. A linear trendline is one segment. The ideal curve is the documented LS fit (category (a),
  the same precedent as `trendline-origin-*`); the render is accurate to about 1 px.
- [Spec] ECMA-376 `c:trendlineType` is one of `exp | linear | log | movingAvg | poly | power`, with `c:order` 2..6 and
  `c:period`; `c:smooth` is a boolean on a series; `c:logBase` allows 2..1000. The spec names the types but does not
  print the fit formulas; the LS definitions above are the measured ones.

## Other things noticed

1. **Power trendline with a data-determined real exponent.** [Measured] The power trendline is LS in log-log, so `b`
   is a combination of logarithms of the data (two points give `b = ln(y2/y1)/ln(x2/x1)`, for example `log_2 3`).
   `Defs.lean`'s `power_law` takes rational `b`. This route would give `y = a x^b` with `b` a quotient of logs of
   rationals. Whether such `b` is `PConstructible`, and whether the curve is already derivable, is [Open]. The
   exponential trendline likewise gives `y = a r^x` with any base `r` from data.
2. **Gompertz-type sigmoid.** [Pieces measured, composition Heuristic] `a e^{b 2^u}` with `b < 0` on a log-2 axis is
   the double exponential `a exp(-c 2^u)`, a monotone S-shaped curve; reverse order flips it. It is not the logistic.
3. **Radar as a polar plot.** Exact polar polygon, `r` affine in the value, `theta` uniform in the category index, one
   turn only. A linear fill gives `r = k theta` samples; a growth fill gives `r = e^{k theta}` samples. It is a
   polygon, so intersections yield polygon-vertex algebra, not spiral transcendence (c).
4. **Fill-handle grid density is the real obstacle** to the stacked-spline route: category spacing is uniform in index,
   and a growth series takes its ratio from existing cells, so `h = 0.1` data (`2^{0.1 i}`) needs a ratio cell the
   default chart sheet does not contain. [Open].
5. COM hazards seen: the `Trendline.DataLabel` read and the Histogram chart type each killed PowerPoint, which then
   AutoRecovered several presentations (names like `pptD501.pptx - AutoRecovered`). I did not open or close those, and
   they may belong to P1. Three EXCEL.EXE processes were also left running; I did not start or kill them.
6. Surface/contour exports as a PNG inside the SVG, so 3-D charts are raster, like the earlier 3-D rotation finding.
