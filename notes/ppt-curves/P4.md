# P4: preset shape geometry and motion paths

**Verdict.** **No new curve.** All 186 ECMA-376 preset shapes are built from only `moveTo`, `lnTo`, `arcTo`, `cubicBezTo`,
`quadBezTo` and `close`, so every preset curve is a line, an axis-aligned elliptical arc (category (a), exact in the spec) or a
cubic/quadratic Bézier with controls given by guide formulas. At the default adjust values every guide number is a rational
number, a rational-degree `sin/cos/tan`, a `sqrt` of such numbers, or `sin/cos/tan` of an `at2` of such numbers (that is,
`arctan` of an algebraic number). All of these are already P-constructible (`sqrt_Pconstructible`,
`cos/sin/tan_Pconstructible`, `arctan_Pconstructible` exist in `Basic.lean`). Wave, double wave, heart, cloud, gears, sun, moon,
teardrop, swoosh, the curved arrows and the circular arrows give nothing the `ellipse`, `poly_graph` and `cubic_bezier`
constructors do not already give. PowerPoint's vector render matches the spec definition to 0.12 pt (EMF integer rounding) on
165 of the 177 presets that can be inserted from the enum; the other 12 are limits of my EMF reader, not mismatches.
**Motion paths: negative.** All 65 built-in motion-path presets are stored as 3-decimal `M/L/C/Z/E` strings (Bézier at best,
category (b); the two spirals are freehand sketches, category (c)). I found no UI read-out channel; the UI-side tests were not
run (see 2.2).

Backends: Python 3 (`xml.etree`, `struct`, `numpy`) for spec/EMF parsing; **no Wolfram** (nothing here needed an identity or a
digit check: every number is a rational combination of standard constants, and the closure facts are Lean lemmas that already
exist). PowerPoint 16.0 via COM, windowless presentation (`Presentations.Add(WithWindow=False)`), observation only
(`AddShape`, `Shape.Export` to EMF, `AddEffect`, `MotionEffect.Path`, `SaveCopyAs`). No UI was driven; `PPT-UI.lock` (held by
another stream) was never taken. Scratch:

## 1. Shape presets

### 1.1 Method

- **[Spec]** `presetShapeDefinitions.xml` fetched from the python-pptx repo
  (`spec/ISO-IEC-29500-1/schemas/dml-geometries/OfficeOpenXML-DrawingMLGeometries/`). That copy has 186 entries; it lists
  `upDownArrow` twice and has no `upArrow` (a typo in that copy; PowerPoint exports an `upArrow`). Guide ops used:
  `val */ +- +/ ?: abs max min mod pin sqrt sin cos tan at2 cat2 sat2`.
- **[Spec, paraphrase of CT_Path2D]** A path is a list of `moveTo`, `lnTo`, `arcTo` (`wR hR stAng swAng`: an arc of the ellipse
  with radii `wR, hR` starting at the current point), `quadBezTo`, `cubicBezTo`, `close`. There is no other curve primitive, so
  the question reduces to the numbers. Category (a) holds for arcs and lines; for the Béziers the control polygon is exact.
- **[Measured]** `survey.py` evaluates every guide at the default `avLst` and classifies the segments. `ang.py` lists every
  `sin/cos/tan` argument at two aspect ratios and checks whether it is an integer number of degrees, or depends on `at2`.
- **[Measured]** Render check: every enum shape (`AutoShapeType` 1 to 183) inserted at 200 x 150 pt, exported to EMF
  (`Shape.Export`, format 5), the `POLYBEZIER16 / POLYGON16 / LINETO / MOVETOEX` records parsed, and the spec anchor points
  compared with the nearest EMF anchor.

### 1.4 Does PowerPoint's render follow the spec? [Measured]

- **Anchors.** On 177 enum presets, the maximum distance from each spec anchor point to the nearest EMF anchor is 0.11 to
  0.12 pt (EMF units are 0.015 pt) for 165 presets, including `cloud`, `heart`, `moon`, `gear*`, `curvedRightArrow`,
  `circularArrow`, `teardrop`, `wave` and `doubleWave`. The remaining 12 (`squareTabs`, `plaqueTabs`, `cornerTabs`,
  `flowChartOfflineStorage`, `actionButton*`, `chart*`, `flowChartPredefinedProcess`, `flowChartInternalStorage`) draw a
  secondary stroke-only path under a second world transform that my parser does not follow; the primary outlines agree. I did
  not chase these. The 9 spec presets with no enum value (`line`, `straightConnector1`, `bentConnector2..5`, ...) were not
  exported; `curvedConnector3` was, via `AddConnector(msoConnectorCurve)`, and its EMF controls are exactly the spec's
  `(50,0) (100,37.5) (100,112.5) (150,150)` for a 200 x 150 pt box.
- **Arcs are rendered as Béziers (category (b) for the render).** The `ellipse` preset is drawn as four standard cubics with
  control offset `0.5522` of the semi-axis. Radial deviation from the ideal ellipse is `2.9e-4` of the semi-axis (`2.7e-4`
  theory plus rounding). So the spec is category (a) for arcs and the render is the usual Bézier fit. The existing `ellipse`
  constructor already carries this standing; nothing is new for these presets.
- `Shape.Nodes.Count` works windowless (ellipse 13, heart 7, rectangle 5) but `Nodes.Item(i)` throws without a window; the
  Edit Points view therefore also shows arcs as cubics (count 13 for an ellipse).

### 1.5 Pitfall noted [Measured]

For `arcTo` in a path whose `w`/`h` differ from the shape, `stAng`/`swAng` are visual angles in **path** space (`atan2` of the
displacement), and the whole path is then scaled non-uniformly to the shape. `cloud` has a 43200 x 43200 path space with
`hR/wR` about 1.36, so applying the angles after scaling puts arc ends 4 pt off; applying them before scaling matches the EMF to
0.1 pt. Not a new curve (a non-uniform affine image of an ellipse arc is an ellipse arc), but anyone re-deriving presets from the
spec must do it this way.

### 1.6 What would count as new, and why nothing does

A preset could be new only through (i) an `arcTo` angle or radius that is a non-algebraic function of the data, (ii) a Bézier
control point with such a coordinate, or (iii) a `sin/cos/tan` whose angle is not (rational degrees) plus (integer multiples of
an `at2` of algebraic data). `ang.py` lists every `sin/cos/tan` argument at the defaults. The non-integer-degree ones are:
340.96135, 199.03865 and 19.03865 deg (`circularArrow` family, `at2` chains), 177.318 and 2.682 deg (`funnel`), 315.176 and
-30.103 deg (`gear6`), 301.635 and -44.969 deg (`gear9`), 33.690 deg = arctan(2/3) (`mathMultiply`, `noSmoking`), 21.468 deg
(`noSmoking`), 119.43 and 97.43 deg (`wedgeEllipseCallout`), 45/7 deg (`swooshArrow`). Each is `arctan` of an algebraic number,
possibly shifted by a rational number of degrees, so its sine and cosine are P-constructible. Non-default `adj` values are
draggable handles and are not exact, so I did not consider them.

The COM enum does not give names, so I did not attach "Spiral Left/Right", "Loop de Loop", "Bounce" or "Curvy" to ids with
certainty. By the order in which Microsoft lists them [Heuristic], 133 and 146 are the two spirals. Whichever ids carry the
names, every motion path in the library is a rounded Bézier or polyline and none is a mathematical spiral, cycloid or sine.
The 3-decimal rounding (0.001 of the slide, 0.01 inch on a 10 inch slide) is itself a departure from the ideal curve.

### 2.2 UI read-out channels [Open, not driven]

No UI automation tool was available to me, and `PPT-UI.lock` was held by another stream, so none of the following was clicked.
What can be said without clicking:

- **Object model.** A motion path is not a shape: `Slide.Shapes` does not contain it, and `Shape.Nodes` exists only on shapes.
  The path is readable only through `MotionEffect.Path`, which is COM and therefore not a UI route.
- **Convert / copy.** I know of no PowerPoint command that turns a motion path into a freeform. Edit Points on a path moves its
  vertices; Copy of a selected path I believe copies the animated object, not the path [Heuristic, still to be clicked].
- **Ghost image.** The semi-transparent end-state image appears only while the path is selected in Normal view. I have no
  evidence that a smart guide or grid snap uses it. If one does, the read-out would be a position only, not a curve.
- **End state.** Slide Show leaves the object at the path end, but that is a screen output. Persisting the end position in
  vector form would need a second shape moved there by hand (typing or dragging; not exact).
- **Raster-only** channels (video, GIF, slideshow screenshots) do not count per the plan.

Verdict for motion paths: no usable read-out found. Even with one, the content would be a rounded Bézier and so could not add
a curve beyond `cubic_bezier`.

## 3. Other things noticed

1. **The `wave` preset is a polynomial graph.** Its top and bottom edges at the default `adj2 = 0` are cubic polynomial graphs
   with rational coefficients, so `poly_graph` (degree up to 6) already describes them; `doubleWave` is the piecewise version.
2. **PowerPoint renders ellipses as four kappa-0.5522 cubics.** The `ellipse` constructor is already an (a)-for-spec,
   (b)-for-render idealization; nothing here changes its status.
3. **Non-uniform path scaling** (1.5): arc angles are measured in the preset's path coordinates. Relevant only if a Lean
   statement ever quotes a preset's arc endpoints.
4. **python-pptx spec copy.** `upArrow` is missing and `upDownArrow` is duplicated; PowerPoint itself exports `upArrow` (a
   line-only polygon, irrelevant here).
5. **Arc pieces versus whole ellipses.** `cloud` has 22 arcs with different radii, all axis-aligned ellipse arcs. In Lean an arc
   piece (rather than the whole ellipse) needs a `restrict` window that isolates it; an arc longer than a half-ellipse may not be
   cut out by a single rectangle. That is a constructor question, not a preset question. [Open]
6. **Text warps.** P1 already covers them; the `prstTxWarp` guide paths use the same guide language and the same segment types.
7. **Where a new curve would have to come from.** Not from preset geometry. Of the exact non-Bézier curves seen in the
   PowerPoint engine, only the chart trendlines (P3) and the two-guide text-warp interpolation (P1) are candidates; the 3-D
   camera is raster only.
