## Findings summary

1. **No route sees the projected curve outline.** Every route that yields a frame, bound, position or vector path gives the box of the projected flat rectangle
   (A) plus a pad of a few raster pixels (about 5 px, so the pad in pt shrinks as 1/DPI). Oval and triangle give identical frames in every route (A-based, 200.52 x 130.32 in EMF),
   even though their outlines project to 188 x 93 and 178 x 104 pt. Wave: frame 200.4 x 129.72; outline 197 x 110.5. Open Bezier (stroked curve, bbox 200 x 80):
   frame 198.7 x 106.9, outline-projection 188 x 105.5 (rect-projection 199.0 x 106.6 fits, curve-projection 188 x 103.8 does not). [Measured]
2. **The true projected outline exists only as raster pixels.** Every 3-D-rotated (even 0.5 degree tilt, perspective with zero rotation, or Z-only 3-D rotation) output of every route is a raster with an alpha/transparent
   background: PNG, GIF, TIFF, SVG (an `<image>` wrapper holding a PNG), EMF/WMF (EMF+ with an embedded PNG), PDF (RGB image + SMask), XPS (ImageBrush). The transparent-pixel
   bbox in those rasters equals the *outline* box B to within 1 to 2 px (0.2 to 0.3 pt at 330 or 200 dpi, 1 to 1.5 pt at 96 to 150 dpi). So the outline ink bbox is *present in the file*, category (b) with error ~ 1/DPI,
   but **no PowerPoint tool reads it back or trims to it**: nothing auto-trims transparent pixels. [Measured]
3. **Tools tested for auto-trimming / ink awareness (all negative):** Remove Background (Manual editing: frame unchanged, marquee stored as fixed 10 % inset t/l=10000 b/r=90000, processed PNG same size, only erases
   some pixels; the auto marking cut the two ends of the ellipse, a heuristic); Convert to Shape on SVG (becomes a picture with a 4-point rectangular `custGeom` equal to the frame, PNG kept);
   Compress Pictures, Crop Fit/Fill/Crop to Shape, Reset Picture: frame-based by design [Spec], not observed to touch ink. [Measured / Spec]
4. **Only XPS exposes any vector path, and it is the frame rectangle** (`Path Data="M 375.48,201.6 L 578.34,201.6 L 578.34,334.26 L 375.48,334.26 Z"` filled with the PNG). PDF places the same image at that box
   (`202.86 0 0 132.66 375.48 205.74 cm`) with the **true slide position** (R1's EMF paste is centred on the slide). So PDF/XPS add a *position* read-out (of A + 3 pt) to R1's width/height. [Measured]
5. **Fixed DPI per route; not tunable.** `ExportBitmapResolution` (96 and 600 tested; originally unset, restored by deleting the value) changes nothing in any route:
   Save As Picture 330 dpi (UI), `Shape.Export` PNG/GIF/JPG/BMP 96, Paste PNG 150, Paste JPEG 120, Paste Bitmap/GIF/SVG 96, PDF/XPS 200, EMF 600. A 600 x 360 shape gives the same dpi. [Measured]
6. **Unrotated shapes** (flat): SVG paste is a real vector `<path>` (377 bytes); EMF is the vector EMF+ of R1. Any 3-D camera, however mild, switches the output to raster. [Measured]
7. **Word/Excel:** Excel `PasteSpecial` of EMF/PNG/JPEG/GIF/Bitmap/WMF/SVG reproduces the PowerPoint frames (EMF 200.40 x 130.20; Excel rounds to its own EMU grid, 0.12 off R1's 200.52 x 130.32).
   Word `Range/Selection.PasteSpecial(DataType=...)` ignored every DataType and pasted the native 200 x 120 shape (flat size; no projected read-out). [Measured]

## Details

### 1. Paste Special formats (COM `Shapes.PasteSpecial(dt)`, dt 0..12) [Measured]
Oval, same shape, same session: frames (w x h, pt) EMF 200.52 x 130.32 (centred on slide: left 379.74 top 204.84), PNG 202.097 x 132.011, JPEG 202.8 x 132.6, GIF and SVG 204.0 x 133.5,
Bitmap 203.974 x 133.483. Only the EMF paste is centred; PNG/Bitmap land at the shape's own projected position (about (379, 204)), JPEG/GIF/SVG with offsets of 24 pt multiples
(paste cascade), so the only position information is in PNG/Bitmap-type pastes and it is shifted by the pad. Wave frames are 0.4 to 0.6 pt shorter in height than the oval's
(the wave's own flat visual bbox is slightly shorter than its rectangle); triangle = oval exactly. The unrounded reading: width px = ceil(A_px) + 4 to 6 for every raster route.

DPI per route (from the file headers): PNG 150, JPEG 120, GIF/SVG/Bitmap 96. Pad in pt = about 5.3 px x 72 / dpi (96: 4.2 pt, 120: 3.0, 150: 2.3, 330: 1.1, 600: 0.725). The PDF route is the exception: 3.0 pt (8.8 px at 200 dpi).

### 2. Save as Picture (UI dialog "Save As Picture", types PNG, JPG, GIF, TIF, BMP, SVG, EMF, WMF) [Measured]
Driven through the real dialog by UIA (selected shape: the rotated oval; `ExecuteMso('ObjectSaveAsPicture')`). Files: `sap3\`. All 330 dpi (PNG metadata 329.9968).
Oval 200 x 120: image 921 x 599 px. A_px = 916.0 x 594.3, so pad about 5 x 4.7 px. Alpha bbox (px): PNG/TIF (28,85,895,518), 128-threshold (29,87,894,516); GIF (29,86,894,517); JPG/BMP non-white (28,86,895,517).
Ink 188.73 x 93.60 pt (alpha 128) against B = 188.41 x 93.50: error 0.32 and 0.10 pt (about 1 px). 600 x 360 shape: 3174 x 1801 px, ink 2646 x 1316 px = 577.4 x 287.2 pt vs B 576.98 x 286.66.
**No auto-trim**: the transparent margin (28 px left, 85 top) is kept; the bitmap is the whole projected-rectangle frame. SVG output is `<svg width=921 height=599>` with one `<image>` (the PNG) and a clip rect; EMF = raster EMF+.
A caution that cost me a run: `ExecuteMso` acts on the *application's* active window; with other streams sharing the instance the first attempts saved another stream's rectangle (275 x 184 px). Activate the window and select the shape in the same process first.

### 4. Camera-mild cases: when does the output become raster? [Measured]
Same oval, EMF and SVG paste: flat -> SVG `<path>` (377 B), EMF vector 1172 B; Z-only 3-D rotation 30 degrees -> raster EMF 3.8 MB, frame 233.88 x 204.60 (bbox of the *rotated rectangle*:

X = 40 ortho: raster, 153.96 x 120.60. So it is the *presence of a 3-D camera scene* that triggers rasterization; the 2-D rotate-by-degrees tool stays vector. [Measured]

## Other things noticed

* **The pad is pixels, not points:** ~5 px at every dpi except PDF (8.8 px at 200 dpi, 3.0 pt) and EMF (6 px). A route with higher DPI would have smaller pad; the 600-dpi EMF is the best of the measured routes, 330-dpi Save As next.
* **Ink is in the file:** for a measurement that needs the *outline* box B, the data exist in every Save As / paste raster as the alpha-channel bbox. A user cannot read it back inside PowerPoint (no trim), but a screenshot/External tool could; within the rules (UI-only constructions) it is not a construction.
  Candidate UI trim routes I could not exercise: AI-assisted Remove Background; Crop with manual drag to the ink edge (user-dependent); Word/Excel Crop; Snipping.
* **PDF structure tree** carries the unrotated frame `[380 210 580 330]`: vector numbers, but they are the flat bounding rectangle.
* **Paste cascade offsets (24 pt) and 'centre on slide':** only the EMF paste centres. PNG/Bitmap pastes keep the projected position (about the shape's own position, offset 1 to 2 pt from A's corner).
* **pywinauto side effect:** importing pywinauto in the same Python process as `win32com.client.Dispatch` broke dynamic COM dispatch (`AttributeError: Presentations`); keep COM scripts and UIA scripts in separate processes. pywinauto also needs `SetProcessDpiAwareness(2)` (display is 150 %); otherwise coordinates are scaled by 1.25.
* **Shared instance hazards:** `ExecuteMso` and `Copy` act on the application's active window/clipboard; the `Paste Special` dialog route via `ExecuteMso('PasteSpecialDialog')` + UIA clicked OK but pasted nothing in my window (not diagnosed), so UI Paste Special formats are covered by `PasteSpecial(dt)` only; the dialog's format list is: Microsoft Office Graphic Object, Picture (SVG), (PNG), (Enhanced Metafile), (JPEG), (GIF), Device Independent Bitmap, Bitmap.
* **COM `Shape.Export` with ScaleWidth/ScaleHeight** gave tiny nonsensical sizes (60 x 43 px for ScaleWidth 200); not pursued.
* **Open:** video export; AI-assisted Remove Background; Word UI Paste Special; Copy-back into PowerPoint; PDF through the File > Export UI; whether a pixel-quantized ink box could be obtained by a UI Crop-by-drag snapping to picture content (it does not snap in my knowledge, [Heuristic]); the 0.2 pt unequal pad of PDF/XPS per side.
